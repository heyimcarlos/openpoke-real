Why there are two queues

agent_runs

Unit: one serialized conversation turn.

Created by: durable Thread ingress.

Claimed by: conversation-agent workers.

Purpose: reconstruct context and decide what the user-facing agent does next.

execution_tasks

Unit: independent delegated work or one runnable Workflow Step.

Created by: trusted delegation or Workflow Kernel code.

Claimed by: execution workers.

Purpose: run bounded deterministic or reasoning execution.

They cannot safely be one queue because they have different serialization and capacity rules. Agent Runs serialize per Thread. Execution tasks are globally and per-tenant bounded, and may run independently.

Exactly how a queued Agent Run appears

Existing Thread state What new ingress does Reason
No queued or running run Insert one agent_runs(status='queued') row. There is unread work and no active owner.
A run is already queued Increase its ingress_cutoff. Coalesce a burst into one model turn.
A run is running Append ingress, but create no second active run yet. Preserve one queued or running run per Thread.
The running run completes and newer ingress exists Insert the next queued run in the completion transaction. Prevent a lost wake-up while keeping the current cutoff frozen.

The database backs this rule with a partial unique index on agent_runs(thread_id) for statuses queued and running.

Check your model

Who decides that Step B is runnable?

The deterministic Workflow Kernel. Neither RabbitMQ, queue order, an agent, nor a worker owns that decision.

What is the conversation-agent worker pool?

Disposable replicas polling agent_runs. A worker reconstructs one frozen Thread context, runs one bounded interaction turn, and commits only through its current lease.

Why does an execution result create another Agent Run?

The specialist result is durable input, not the final user-facing response. The serialized conversation agent consumes it and decides how to present it or what to do next.
